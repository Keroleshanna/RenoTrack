Branch `feature/phase-8-invoices-payments-project-completion`, off `main` at `697292b`, tip `4218fcc`, **merged via PR #14 (merge commit `0c12948`)**. **Do not reopen these without new evidence — each was decided explicitly before implementation:**
- **`InvoiceLine` is deferred entirely.** No Domain type, table, configuration, repository, DTO or migration content in Phase 8. ERD.md's own "an Invoice can exist with just header-level Net/VAT/Gross amounts if lines aren't needed" is what makes a line-less Invoice legal. The per-rate VAT split is computed to derive the header totals and then discarded. **Revisit trigger:** a concrete use case needing stored line detail — most likely Phase 14's §14 UStG PDF template, which is where BR-5's "description/quantity" requirement is actually enforced.
- **Phase 8 supports full payment only.** `Invoice.MarkPaid` takes no amount and always records `GrossAmount`; a reflection test asserts no `Money` appears in its signature. FR-8.4, Sequence Diagram §9's `{ paidAt, method }` body and Wireframe E3 all offer no amount to supply. **ERD.md's one-Invoice-to-many-Payments cardinality is forward-compatibility, not evidence that partial payments work** — what a partial payment does to `Invoice.Status`, whether a per-invoice outstanding balance is tracked, and what happens on overpayment are all unspecified. Pinned by tests so the schema cannot be mistaken for the semantics.
- **The VAT allocation is per-rate and proportional to the originating Angebot's gross rate mix**, never a blended rate, and must satisfy `sum(Net) + sum(VAT) == GrossAmount` exactly with deterministic, tested residual-cent handling. `Invoice.Create` enforces the equality as a structural invariant (Slice 1), so Slice 3's arithmetic cannot lose or invent a cent silently.
- **A void reason is required from every source state, including `Draft`.** StateMachine.md §3.3's blank guard cell was a documentation omission and has been reconciled there.
- **There is no `Invoice.SentAt`.** `Angebot` has one; ERD.md's `Invoices` table defines none. A test asserts the property's absence.
- **`DueDate` is not constrained in any way**, including against the issue date. An earlier draft of Slice 1 added such a guard by analogy with `Project.Create`'s non-negative `AgreedTotal`; it was removed before approval because no requirement document constrains a due date, and analogy is not documentation. **Do not reintroduce it without a documented rule.**
- **`Invoices.ProjectId` must never become unique.** One Project has many Invoices (ERD.md §4), which is the whole of FR-8.1's splitting feature. Pinned by a LocalDB test.
- **The Project invoice-balance read is Admin `F` / Inspector `R` — Project financial-summary data, and `PermissionMatrix.md` §5 now has the row.** Decided in Slice 3 after finding the permission undocumented. **This governs Slice 6's `ProjectDetailDto` too**: the same Agreed/Invoiced/Remaining figures are Inspector-readable there. It confers **no** Invoice-management permission — create/send/mark-paid/void stay Admin-only, and one API test asserts both halves so they cannot drift apart. Read-only but **unscoped**: no `IOwnershipValidator`, no per-Inspector filtering.
- **A positive Invoice against an Angebot whose gross total is zero is a 409**, because no proportion exists to allocate by. **Kept as narrow as the arithmetic:** a *zero-gross* Invoice against the same Angebot is still allowed, zero-gross Angebote remain valid, and zero-valued Projects remain valid. No VAT rate is invented in any case.
- **BR-3 is a warning, never a block, at every layer.** No comparison against `AgreedTotal` in the handler, no validator maximum, no clamping of `Remaining`, no warning flag on the DTO. The negative number *is* the warning. Six adversarial experiments in Slice 3 pin this and the authorization boundary; see `PHASE8_PROGRESS.md`.
- **Invoice numbers are unique and never reused but not gapless (D66)**, and are reserved *after* every pre-evaluable guard. Four tests assert the sequence is untouched on each rejection path. `Architecture.md` §8 was corrected — it previously claimed gaplessness the mechanism cannot provide, and mis-cited BR-5 for BR-9.
- **`.Amount` on a value-converted `Money` property does not translate inside an EF Core aggregate or correlated subquery** — only in a plain projection. `ProjectQueries.GetInvoiceBalanceAsync` uses `EF.Property<decimal>` and two statements for this reason. Found by tests failing, not inspection; expect the same constraint in any future `SUM` over a money column.
- **The public invoice link is read-only and is never consumed.** `PermissionMatrix.md` §7 grants the customer "View Invoice via token link" and nothing else, so **no Invoice decision action exists** and `UsedAt` is never set on an Invoice link. BR-4 mentions "an Invoice's decision-type action" hypothetically; none is documented, and none was invented. `GET /api/v1/public/invoices/{token}` therefore checks existence, entity type and expiry — never prior use.
- **`PublicInvoiceDto` carries a dedicated `PublicInvoiceStatus` (`Open`/`Paid`/`Void`), decided in Slice 5.** Never the internal `InvoiceStatus`; `Draft`/`Sent`/`Overdue` all collapse to `Open`, because exposing a dunning state is a decision no document makes. **`Paid` and `Void` do not invalidate the token link** — it stays readable and simply reports what happened. `VoidReason` stays internal: the customer is told *that* the invoice was cancelled, never the staff wording. Four tests across two layers pin this.
- **`Payments` cascades from `Invoices`; every other FK in this schema is `Restrict`.** That is aggregate composition, matching `Angebot`→`Sections`, `AngebotSection`→`Items` and `Inspection`→`Photos`, not a departure from CLAUDE.md §21 (which governs references *between independent aggregates*). It is deliberately **not** covered by a test: nothing in this schema is ever hard-deleted, so the behaviour never triggers.

- **The Project completion guard has two clauses, and the second one is a rule no document stated (D67, Slice 6).** A Project is blocked when it has **no Invoices at all**, **or** at least one Invoice is `Draft`, `Sent` or `Overdue`. `Paid` and `Void` never block. The status clause resolved a **three-way contradiction** — `StateMachine.md` §4.3 (a `Draft` blocks), §3.4 four sections later (it does not), and `Sequence Diagram.md` §10 (a `Void` blocks, contradicting both) — in favour of §4.3, with §3.4 corrected, §10 annotated and the whole reconciliation recorded in `StateMachine.md` **§4.4**. The zero-Invoice clause exists because "all Invoices are `Paid` or `Void`" is vacuously true over an empty set, which would let a never-invoiced Project close silently in exactly the case the guard exists for. **Do not "simplify" either clause.**
- **The override reaches the invoice precondition and nothing else.** No value of `forceOverride` completes a Project that is not `Active` — that guard lives inside `Project.Complete()` where no request field can reach it. Pinned by tests for both `OnHold` and `Completed`.
- **`forceOverride` with nothing to override is a 400 and writes no audit entry.** An override must override something; recording a reason against a Project that had nothing outstanding would be a false justification in the one record FR-8.6 exists to produce. **A reason without `forceOverride` is likewise rejected, never silently dropped** — the accept-and-discard pattern Phase 6 refused for FR-6.3.
- **The FR-8.6 override reason is stored only in `AuditLog.Details`, and that inherits D50's best-effort semantics.** `ERD.md`'s `PROJECT` defines no column for it, and `StateMachine.md` §4.3 assigns it to the AuditLog, so no schema was invented — but `AuditService` swallows its own failures, which means **a failed audit write loses the reason silently while the Project stays completed**. This is a known limitation, deliberately accepted rather than solved (D67). **Revisit trigger:** any requirement that reads an override reason back, or any compliance audit of completed Projects; the alternative already costed out is a `Projects.CompletionOverrideReason` column and a ninth migration.
- **FR-7.4's invoice figures are duplicated between `GET /projects/{id}` and `GET /projects/{id}/invoice-balance`, deliberately**, because FR-7.4 requires the detail page to carry them "in one place". An Infrastructure test asserts the two agree, so the duplication cannot drift. **Voided Invoices appear in the detail read's invoice list** (BR-9 — a numbered record, not a deleted one) and are excluded from `alreadyInvoiced`/`remaining` only. The list is ordered `IssueDate` then `Id`; no document specifies an order, and `IssueDate` is not unique.
- **The invoice list on the Project detail read is Inspector-visible**, as Project-detail data (`PermissionMatrix.md` §5's clarified row) — and confers no Invoice-management permission. One API test asserts both halves together.

**Known gaps deliberately carried by Phase 8's own design (not oversights):**

An Admin endpoint, a `BackgroundService` and read-time derivation were each considered and **each explicitly rejected** — do not invent a hosting mechanism to make `PROJECT_ROADMAP.md`'s Phase 8 line appear complete.

Reserved as late as practical, after every pre-evaluable guard. **No claim is made about what German law requires** — if legal gaplessness becomes a confirmed requirement, that is a separate design.
- **`PutOnHold`/`Resume` still have no Application or API surface**, and are assigned to **no phase**. Phase 8 deliberately does not claim them. **Slice 6 surfaced a consequence worth knowing before that changes:** `Project.Complete()` refuses anything but `Active`, so if on-hold ever ships without resume, an `OnHold` Project could be neither resumed nor completed. Unreachable today only because nothing can put a Project on hold either.

## 1h. Phase 9 — Design Approved, Implementation Not Started

Branch not created. **`PHASE9_PROGRESS.md` is the authoritative record** of the eight decisions (F1–F8) approved on 2026-08-09 before any code, plus the slice plan and the repository facts the design depends on. Permanent decision record: **`ARCHITECTURE_DECISIONS.md` D68–D71**.

**SRS OQ-3 no longer blocks Phase 9.** It was split: **OQ-3a — transport — is resolved as SMTP via MailKit** behind the unchanged `IEmailSender`; **OQ-3b — the production mailbox, sender identity and Admin recipients — is deferred to deployment**, because no company mailbox exists yet and, by decision, no company-specific value is compiled in or given a default. A company mailbox and a transactional provider's SMTP relay are the same implementation with different configuration, so a vendor chosen later changes no code (D68).

**Do not reopen these without new evidence — each was decided explicitly before implementation:**
- **A committed business operation stays successful when its email fails**, on every flow **including the two anonymous ones** (the website contact form and the customer's token-link decision). The API never turns a delivery failure into a 500 (D69).
- **The failure is persisted, not merely logged** — one **Infrastructure-owned** `NotificationDeliveries` table (migration #9). **As built the lifecycle is `Pending → Sending → Sent | Failed`**, with `Failed → Sending` and `Sending → Sending` reachable only by a manual retry; `Sending` arrived in Slice 5 and needed no migration. Logging alone is insufficient *because* two senders are anonymous endpoints where no Admin is present to be told (D69).
- **The row is written after the business commit, not inside it.** The resulting crash window — commit succeeds, process dies, notification record lost — is an **accepted, documented trade-off**, not an oversight. Fixing it means an Outbox, which was explicitly rejected. Revisit on a real incident, not on principle.
- **No Outbox, no message broker, no queue, no `BackgroundService`/`IHostedService`, no dispatcher.** None exists in `src/` today; Phase 9 adds none. `Architecture.md` §10's earlier "queued/retried" wording was corrected to match.
- **Retry is manual, Admin-triggered, synchronous** — no automatic retry, no backoff, no attempt cap — and it re-sends **only the notification**, reconstructed from persisted business data. **It never re-executes the business operation** (D70).
- **Duplicates are acknowledged, not eliminated.** An ambiguous transport failure may yield a duplicate on retry; that is accepted, because every notification is content-idempotent. No message-ID deduplication is introduced. Admin double-clicks are handled by the status transition alone (D70).
- **Admin notification recipients are a configured list**, deliberately independent of the Identity Admin role. **No `IUserQueries` lookup is added for this** — holding the Admin role does not subscribe an account to operational mail (D71).
- **The notification record is Infrastructure-owned** — no Domain `Notification` aggregate, no delivery state on any existing aggregate. The Domain stays unaware of email entirely (D69, D49's test applied unchanged).
- **No retention policy.** Notification rows remain until a real requirement exists; no 30/90-day deletion and no archival job was invented.
- **Six templates, not five.** `Architecture.md` §10 named five; `IEmailSender` has had six methods since Phase 2. The sixth (changes-requested, to the Inspector) is from Sequence Diagram §5 — a documentation gap, now corrected. Producing six is not scope creep.
- **Phase 9 is the complete delivery workflow**, not SMTP integration only (F7). Slices 1–3a deliver FR-9.1/9.2/9.3; slices 3b–5 exist for the approved visibility-and-retry requirement, which goes beyond the roadmap's original Phase 9 wording.

**New permissions:** `PermissionMatrix.md` §9 — *view failed/pending notifications* and *retry a notification*, both Admin `F` / Inspector `—`, no ownership validation (they are `F`, so per §16 no `IOwnershipValidator` belongs in their handlers).

## 4. Decisions Considered Final (Do Not Reopen Without New Evidence)

- Clean Architecture layering + explicit (not transitive) cross-project references.
- No MediatR; hand-rolled `ICommandHandler<TCommand, TResult>`.
- No AutoMapper; manual `ToDto()` extension methods.
- Rich domain model with private constructors, named transition methods, self-guards only.
- `IOwnershipValidator` as named-business-intent methods, never a generic id-comparison helper.
- Audit policy: business milestones only, targeting the aggregate the business cares about (not necessarily the one directly mutated).
- Notification models are dedicated types in `Common.Notifications`, never feature DTOs.
- Repository/interface/DTO growth strictly on-demand, never speculative.
- Role-based authorization (API layer) vs. resource ownership (`IOwnershipValidator`, Application layer) — decided mechanically by PermissionMatrix's `F`/`S` marking.
- The Application layer generates stable external identifiers before invoking external infrastructure, when doing so lets a Domain guard reject before an irreversible side effect.
- Never truly delete a historical record (retire/void instead) — applies project-wide by default for any future "delete" requirement, not just the specific entities where it's already been formalized (Lead, Invoice, Inspection, CatalogItem).
- No CatalogItem command uses `IOwnershipValidator` — every action is Admin/Inspector-`F` per `PermissionMatrix.md` §6, confirmed during Slice 11's design review.
- `IQueryHandler<TQuery, TResult>` is a distinct interface from `ICommandHandler<TCommand, TResult>`, even though their method signatures currently coincide — queries get their own dispatch abstraction, not a reuse of the command one (`ARCHITECTURE_DECISIONS.md` D36).
- `SearchCatalogItemsQuery` starts with no `includeRetired` parameter — always excludes retired items, no flag until a real documented use case needs one (`ARCHITECTURE_DECISIONS.md` D37).
- A retired `CatalogItem` remains a valid direct `CatalogItemId` reference — retirement only affects discovery, never a direct reference (BR-14, `ARCHITECTURE_DECISIONS.md` D38).
- `AddAngebotItemCommand`'s `Quantity`/`UnitPrice`/`VatRate` are always caller-supplied for both paths; only `Description`/`Specification`/`Unit` are copied from a `CatalogItem` in the Catalog-sourced path.
- `SaveAngebotItemAsCatalogItemCommand` is out of Phase 2's scope and deferred — not a rejection of the feature, just a scope/sequencing decision (BR-14 is unrelated and stands; `ARCHITECTURE_DECISIONS.md` D39).
- No generic `Repository<TEntity>` base class for Infrastructure repositories — hand-written, per-aggregate classes only, matching the project's consistent anti-generic-abstraction stance.
- `RenoTrack.Infrastructure.Tests` uses real SQL Server LocalDB, never the EF Core InMemory provider (`ARCHITECTURE_DECISIONS.md` D40).
- Migrations are regenerated from the model when the model changes, never hand-edited — the migration is a product of the model, not a separately-maintained artifact.
- `IUnitOfWork`'s Infrastructure implementation is an intentionally thin, one-line wrapper over `SaveChangesAsync` — no transaction API, no `IDisposable` (`ARCHITECTURE_DECISIONS.md` D48).
- User-referencing FK constraints (`AssignedInspectorId`, `InspectorId`, `CreatedByInspectorId`, `ReviewedByAdminId`, `AdminUserId`) were deliberately deferred until the Identity slice — not an oversight (`ARCHITECTURE_DECISIONS.md` D44) — and are now real constraints as of Slice 15.
- A component performing several independent units of scoped work outside a single request (e.g. multi-item startup seeding) is a dedicated DI-registered class with `IServiceScopeFactory` injected via its constructor — never a static utility, never `IServiceScopeFactory` as a per-call method parameter (`ARCHITECTURE_DECISIONS.md` D55, `CLAUDE.md` §21).
- `RenoTrack.Infrastructure.Tests` keeps using real LocalDB in CI too, never a weaker substitute for pipeline convenience — CI is split by OS (Linux for build + database-free tests, Windows for database-backed tests) instead (`ARCHITECTURE_DECISIONS.md` D56). `RenoTrack.Api.Tests` joined the Windows job in Phase 4 Slice 1 for the same reason (D58).
- API versioning is a literal `api/v1` URL segment with no versioning library; a future v2 is added as parallel v2 controllers, not via version negotiation (`ARCHITECTURE_DECISIONS.md` D57).
- DI registrations in **both** composition roots (`AddApplication()`, `AddInfrastructure()`) are explicit and uniformly Scoped — never assembly scanning, never Scrutor, never `AddValidatorsFromAssembly`. The "forgot to register" risk is covered by a reflection-based test, not by scanning production code. Note `ValidateOnBuild` alone does **not** catch a missing handler registration while nothing depends on it — do not weaken `DependencyInjectionTests` into a plain container-build check.
- `AddApplication()` takes no `IConfiguration` and must not acquire hosting/configuration concerns; Application's only packages are FluentValidation and `Microsoft.Extensions.DependencyInjection.Abstractions`.
- Authentication is deliberately outside the CQRS pipeline — `AuthController` calls `UserManager`/`ITokenService` directly, and `ITokenService` lives in Infrastructure rather than `Application.Common.Interfaces`. This is not an inconsistency to tidy up (`ARCHITECTURE_DECISIONS.md` D60).
- Production never mutates database schema at application startup; migrations are applied by an explicit deployment step and startup verifies migration history (both directions) plus required roles, refusing to serve otherwise. `Migrate` is a Development opt-in and is hard-refused in Production. No mode skips verification, and no code path provisions a user (`ARCHITECTURE_DECISIONS.md` D63).
- Login failures must stay indistinguishable from one another (unknown email, wrong password, inactive, locked out → the same 401). Do not make those messages more helpful.
- Refresh tokens are stored as SHA-256 hashes only, rotated on every use, with whole-chain revocation on reuse. There is deliberately no logout endpoint and no cleanup job; retention is until `ExpiresAt`, and revoked-but-unexpired rows must be kept or reuse detection breaks.
- `AuthController`'s `IsLockedOutAsync`/`AccessFailedAsync`/`ResetAccessFailedCountAsync` calls **are** SRS FR-10.3's implementation — `CheckPasswordAsync` does not touch lockout counters. Removing them silently removes a documented security requirement.
- `RenoTrack.Api.Tests` boots the real application via `WebApplicationFactory<Program>` against real LocalDB, with schema created by `MigrateAsync()` — deliberately **not** `EnsureCreated()` as `RenoTrack.Infrastructure.Tests` uses. Do not "unify" the two fixtures for consistency: the projects have different responsibilities, and `EnsureCreated` would break outright if startup-time migration were ever chosen (`ARCHITECTURE_DECISIONS.md` D58). Slice 11 settled that question — Production startup never migrates (D63) — and `Api.Tests` keeps `MigrateAsync` unchanged, so D58 stands exactly as written.

  4. **Reassign an Inspection to a different Inspector** (§2, Admin `F`). No endpoint and no Domain method — `Inspection` has no reassignment transition at all, so this would need a Domain change and a `StateMachine.md` entry, not just an endpoint.
  5. **Change own password** (§8, Admin `F` / Inspector `F`). No endpoint. Identity's `UserManager` supports it; nothing exposes it. Related to but distinct from **SRS OQ-1** (Admin managing *other* accounts), which is separately unresolved.
  - **Do not build any of these speculatively.** Each needs a documents-first decision about which phase owns it, and #4 additionally needs a Domain design. They are recorded so the permission matrix and the API can no longer drift apart silently.
- **Authenticated photo-serving endpoint + `IFileStorage.GetAsync`.** `Architecture.md` §9 says photos are "served back through an authenticated API endpoint rather than direct static file exposure." Neither exists. **The system can store photos it cannot serve.**
- **Upload size limit** is Kestrel's ~30 MB default. No project-specific limit was invented because no document states one; recorded so the effective cap is known rather than assumed.
- ~~**`PATCH /api/v1/inspections/{id}` (edit Inspection notes) — documented, built, and unreachable.**~~ — **resolved in Slice 10.** The endpoint now exists, and `Architecture.md` §5.2 gained the row it had been missing, so the Architecture-vs-PermissionMatrix/Sequence-Diagram disagreement is closed. **`UpdateInspectionNotesCommand` is no longer an unreachable handler**; every remaining unreachable one belongs to Phase 5/6 and is correctly out of Phase 4's scope.
- ~~**Lead `Won`/`Lost` have no endpoint**~~ — **resolved in Phase 6, and still without an Admin-driven path.** Both transitions now happen exactly where `StateMachine.md` §5 requires: inside `RecordAngebotDecisionCommandHandler`, in the same `SaveChangesAsync` as the Angebot decision and the token consumption. `Lead.MarkAngebotSent()` is called by `SendAngebotCommandHandler`, so `AngebotSent` is reachable and the guard is real rather than vacuous. **The standing prohibition is unchanged: do not add an Admin `MarkWon`/`MarkLost` endpoint** — it would be a second path to a decision BR-4 exists to make tamper-proof. `AuditAction` gained `AngebotCustomerApproved`/`AngebotCustomerRejected` rather than `LeadWon`/`LeadLost`, named for the event and logged against the Lead (see the enum's own doc comment).
- **`AuditService.LogAsync` is not write-isolated — it shares the request's `DbContext`.** Found empirically during Slice 9's second adversarial experiment, where it masked a deliberately-introduced defect by flushing an unrelated pending mutation along with the audit row. D50's "commits its own write independently" means independently of `IUnitOfWork`, **not** in a separate context. **Benign today** — every handler calls `LogAsync` after its own `SaveChangesAsync`, which is D50's own stated precondition, so nothing is ever pending — but a handler that ever had uncommitted changes at `LogAsync` time would have them committed silently, inside a `try`/`catch` that swallows failures. Not changed in Slice 9 because it alters no current behaviour. **Revisit trigger:** any handler that would call `LogAsync` with pending changes, or any change to the audit-write mechanism. It is also a further reason not to reorder `CompleteInspectionCommandHandler`.
- **A status-code-only assertion cannot distinguish a role-gate 403 from an ownership 403.** Found in Slice 9's third adversarial experiment: weakening the action's `[Authorize(Roles = Roles.Inspector)]` left the Admin test passing, because the class-level attribute admits both roles and `EnsureInspectionOwnership` then produced the same 403. This is exactly the attribute-vs-guard drift `CLAUDE.md` §22 requires both layers to be kept against. The fix — asserting the 403 body is **empty**, since an authorization-middleware rejection carries no body while a `ForbiddenException` yields ProblemDetails — is what makes such a test detect the drift. **Any future endpoint whose role gate and ownership check would produce the same status code needs this assertion, or its authorization test proves nothing.**

**Known technical debt, verified as still present at the time of writing:**

- **`Roles.cs` folder/namespace mismatch.** The file is `src/RenoTrack.Api/Auth/Roles.cs` but declares `namespace RenoTrack.Api.Controllers` (so `[Authorize(Roles = ...)]` interpolation resolves without an extra `using`). Cosmetic, deliberately left twice rather than widening an unrelated diff. **Confirmed still present.**
- **Orphaned files remain possible.** Slice 8's compensating delete is best-effort: a process crash between the file write and the compensation, or a failing delete, still leaves a file with no row. This is compensation, **not** atomicity — do not document or extend it as a consistency guarantee. No sweeper exists; the retention rule (delete anything past `ExpiresAt` for refresh tokens; orphan files have no equivalent rule yet) is recorded in D60 for tokens only.
- **Refresh-token rows are never cleaned up.** Retention is until `ExpiresAt` by design, with no background job — steady state is a few hundred rows (D60). Revisit at tens of thousands, or an order-of-magnitude user increase.
- **`IUserQueries.IsActiveInspectorAsync` returns a single boolean deliberately** — keeping it atomic is a safety property, since a split would let a caller check two of three conditions. **Revisit trigger:** when Phase 10 introduces the Inspector picker, an Admin can select a deactivated Inspector through normal use rather than by typo; at that point reconsider whether "exists but ineligible" should be distinguishable from "nonexistent", and redesign the *result* rather than splitting the check.
